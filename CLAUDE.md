# MAX-бот диспетчерской колледжа

## Цель проекта
Бот (позже ИИ-агент) в мессенджере MAX, который принимает заявки в диспетчерскую колледжа по техническим проблемам. Первый этап: пилот в своём колледже. Дальше: превращение в тиражируемый продукт для организаций с диспетчерской (колледжи, вузы, школы, УК, бизнес-центры) с помесячной подпиской.

## Что уже решено
- Бот собирает только: номер корпуса, кабинет, суть проблемы, контакт заявителя в MAX.
- На старте бот работает на личном профиле владельца. Если колледж заинтересуется, бот будет продан колледжу.
- Тестирование только локально, чтобы не собирать персональные данные.
- Нужны БД и дашборд для руководства: скорость выполнения, число закрытых и незакрытых заявок, кто больше закрывает.
- Нужно автоопределение категории заявки.

## Предлагаемый стек (можно менять)
- Python 3.11+
- Библиотека `maxapi` (неофициальная, в стиле aiogram: Dispatcher, Router, фильтры, FSM, polling и webhook)
- SQLite на старте, структура должна легко переезжать на PostgreSQL
- Дашборд: простая веб-страница (FastAPI + шаблон или статический HTML с графиками)
- Токен бота только через переменную окружения `MAX_BOT_TOKEN`, не коммитить в репозиторий

## Заметки по MAX Bot API
- Бота создают через Master Bot (@Masterbot) в MAX, он выдаёт токен.
- При создании есть модерация и требования к оформлению и функционалу бота. Прочитать на https://dev.max.ru/docs-api/ до публикации.
- API: HTTPS-запросы на botapi.max.ru, токен передаётся как access_token.
- К сообщениям можно добавлять кнопки (inline, callback). Использовать кнопки для выбора корпуса и категории.
- При тестировании в групповом чате боту нужны права администратора.
- Если у бота есть активные webhook-подписки, события через polling не приходят. Для локальной разработки использовать polling.
- Не проверено: нужна ли верификация организации для публикации бота от лица колледжа. Уточнить в документации.

## Сценарий заявки (FSM)
1. Приветствие, кнопка «Новая заявка»
2. Выбор корпуса (кнопки из списка в конфиге)
3. Ввод кабинета
4. Описание проблемы (свободный текст)
5. Контакт заявителя берётся из MAX автоматически, при необходимости уточняется
6. Подтверждение, присвоение номера заявки
7. Уведомление заявителю при смене статуса

## Модель данных (черновик)
- `requests`: id, created_at, building, room, description, category, status, applicant_max_id, applicant_name, assignee_id, taken_at, closed_at
- `assignees`: id, name, max_id, active
- `categories`: id, name (например: электрика, сеть и интернет, компьютерная техника, мебель, сантехника, прочее)
- `status_log`: id, request_id, status, changed_at, changed_by

Статусы: `new` → `in_progress` → `done` (плюс `cancelled`).

## Метрики дашборда
- Количество заявок: новые, в работе, закрытые
- Среднее время до взятия в работу и до закрытия
- Нагрузка и количество закрытых заявок по исполнителям
- Просроченные заявки
- Решено 2026-10-08: график «Заявки по дням» и разбивки по корпусам и категориям на дашборде не нужны, их убрали.

## Автокатегоризация
Сначала простые правила по ключевым словам, затем вызов LLM для неоднозначных случаев. Результат должен быть исправляем диспетчером вручную.

## План работ
1. Каркас бота на `maxapi`, FSM сбора заявки, SQLite
2. Панель для диспетчера: взять заявку, сменить статус, назначить исполнителя
3. Уведомления заявителю
4. Дашборд для руководства (эскиз можно показать колледжу раньше готового бота)
5. Автокатегоризация
6. Вынос специфики колледжа в конфиг (корпуса, категории, исполнители, тексты) для подключения новых клиентов
7. Простая админка для настройки организацией

## Границы на старте
- Никаких интеграций с чужими системами до появления второго клиента
- Только бот, БД и дашборд
- Не хранить лишние персональные данные, только необходимое для заявки

Кнопки: «Взять», «Готово», «Вернуть в очередь», «Категория» (ручная правка) и «Отменить» с подтверждением. Исполнитель заводится автоматически при первом нажатии «Взять». - Сценарий заявителя работает только в личном диалоге (фильтр `InDialog`). Кнопки карточек принимаются в чате диспетчерской и в личке у специалистов (`CardAccess`).

- Этап 4 сделан: дашборд `python -m app.dashboard [--db data/demo.db]`, только 127.0.0.1, без авторизации. Метрики считаются в `app/stats.py`, страница — `app/dashboard/static/index.html` (ванильный JS и SVG, тёмная и светлая тема). Метрики «сейчас» — снимок очереди, «за период» — потоки за 7/30/90 дней. Просрочка определяется по `sla_hours` категории от момента подачи. Персональные данные заявителей на дашборд не попадают.
- Дизайн дашборда (2026-10-13) по референсу Skymetrics (Dribbble): светлая рамка, сайдбар с якорной навигацией (Обзор, Исполнители, Просроченные), крупный заголовок, выбор периода в «пилюле». Четыре карточки за период с бейджем изменения к предыдущему периоду: «Поступило» нейтрально, «Закрыто» рост — хорошо, время рост — плохо. Ниже «Очередь сейчас», «Исполнители», «Просроченные». Шрифт Inter (Google Fonts, запасной — системный). Логотип и название референса не используем. Изменение к прошлому периоду считается в `stats.collect` → `change`.

- Специалисты (2026-10-12): `assignees` с `phone`, `on_duty` и направлениями (`assignee_directions`). Направления — это категории из `org.yaml` (добавлена категория 1С), у специалиста их может быть несколько. Вход: `/staff` → кнопка «Поделиться номером». Принимается только контакт, у которого `max_info.user_id` совпадает с отправителем. Новая заявка уходит в чат диспетчерской (он остаётся для обзора) и в личку специалистам направления, которые на линии. Брать и закрывать заявки можно из лички. Специалистов пока заводят командой `scripts/staff.py`, позже это будет админка дашборда.

Проверка — `app/membership.py` (`get_chat_member`, бот обязан быть админом чата; кэш 10 мин для участников, 1 мин для отказов; ошибка MAX → отказ). Роутер `app/bot/gate.py` подключён первым. `user_removed` сразу закрывает доступ и снимает специалиста с линии. Чат диспетчерской не проверяется. При добавлении в незнакомый чат бот присылает ID в личку добавившему, а не пишет в сам чат.
- Веб-интерфейс с ролями (2026-10-13): вход по 6-значному коду, который бот присылает в личку MAX. Код хранится как хеш, действует 5 мин, даётся 5 попыток, повторный запрос не раньше чем через 60 с; на запрос кода ответ одинаковый для любых номеров. Сессия — cookie `dsess` (HttpOnly, SameSite=Strict), в БД хранится хеш, срок 7 дней. Роли в `assignees.role`: `admin`, `specialist`, `viewer`, права — `app/auth.py` (`ROLE_PERMS`). Руководство не видит имён заявителей и не получает заявки в боте. Действия из веба (`app/actions.py`) обновляют карточки в MAX и уведомляют заявителя. Смена статуса атомарная (условный UPDATE в `repo.set_status`), потому что бот и веб — разные процессы. Защита от CSRF: проверка Origin и обязательный JSON для POST. Демо-база открывается без входа, только просмотр. Первый администратор назначается через `scripts/staff.py role ID admin`.

База без `alembic_version` с уже созданными таблицами не стартует: сначала проверить схему и выполнить `alembic stamp head`. Рабочую `bot.db` проверили и отметили так, копии лежат в `data/backup/`. После правки моделей — `alembic revision --autogenerate`; если миграцию забыли, падает `test_models_match_migrations`. Для SQLite включён `render_as_batch`.

Логотип `app/dashboard/static/logo.png` (щит с градиентом `#558DCA` → `#55B6C5`) — в сайдбаре, на странице входа и как иконка вкладки. Градиент логотипа используется только для украшений: полоска активного пункта меню, полоски в таблице, рамка карточки входа.
- Деплой (2026-10-13): Docker Compose (`Dockerfile`, `docker-compose.yml`, `deploy/Caddyfile`, `deploy/README.md`, `deploy/setup-server.sh`). Сервисы: `migrate` (alembic upgrade head один раз), `bot` (`BOT_MODE=webhook`, порт 8080, путь `/max-webhook`, проверка `WEBHOOK_SECRET`), `web` (дашборд за прокси, `TRUST_PROXY=1`), `caddy` (HTTPS Let's Encrypt). Данные в `./data` (bind mount, UID 1000). Сервер — VPS в России (152-ФЗ). Polling не запускается, если у бота есть webhook: для разработки после деплоя нужен отдельный тестовый бот. Резервные копии — `scripts/backup.py` по cron. Docker Hub может быть недоступен из РФ, поэтому Docker ставится из репозитория Ubuntu и, при необходимости, через зеркало.
- Диспетчерские функции (2026-10-15, миграция `0002`): роль `dispatcher` (заявки, назначение, правка, срок, приоритет, категории; без управления сотрудниками). У заявки есть `priority` (urgent/high/normal/low) и `due_at` (срок, по умолчанию создание + норматив; при ручной правке `due_manual`, тогда смена категории его не пересчитывает). Просрочка во всём проекте считается от `due_at`. История изменений — таблица `request_events` (`repo.log_event`), статусы — по-прежнему `status_log`. Категории — источник правды в БД (`app/categories.py`); `org.yaml` только засевает их при первом запуске; бот (middleware) и веб перечитывают их не чаще раза в 10 с (`categories.refresh`). Карточка показывает приоритет и срок.
- Вход по ссылке-приглашению: `https://max.ru/<бот>?start=staff` (bot_started с payload `staff` или «/start staff») открывает вход сотрудника. Сайт узнаёт имя бота через `get_me` (`/api/public`). Причина «коды не приходят» (2026-10-15): сотрудник не подтвердил номер в боте — по дизайну код не отправляется, а ответ сайта одинаковый для всех номеров.
- Ссылка на профиль: в карточке MAX `max://user/<ID>` (формат HTML). В браузере `max://` открывается, только если стоит приложение MAX, поэтому на сайте есть «Прислать мне в MAX» (бот присылает ссылку в личку). Публичного веб-адреса профиля по ID у MAX нет.
- Решено 2026-10-15: специалист не подаёт заявки (в боте нет «Новой заявки»/«Мои заявки», есть «Взятые мной»); видит все открытые заявки, а закрытые — только своих направлений или взятые им (`visible_to` в web.py, права `VIEW_ALL`, `ANALYTICS` в auth.py); «Обзор» ему недоступен. Время выполнения = `closed_at - taken_at` (`Request.work_time()`), т.е. от назначения исполнителя до «Готово»; срок (`due_at`) по-прежнему считается от подачи.
- Уведомления заявителю (2026-10-15): взята в работу (исполнитель — ссылка `max://user/<ID>`), смена исполнителя, возврат в очередь, выполнена, отменена, смена приоритета, перенос срока (без причины — она только в истории). Тексты в `org.yaml` (`notify_*`), формат HTML. Отправка — `dispatch.tell_applicant`/`notify_applicant`; о собственных действиях заявителю не пишем (`actor_max_id`).
- Репозиторий публичный: имя бота, ID чатов и пользователей в файлы не пишем. ID чата диспетчерской задаётся в `.env` (`DISPATCHER_CHAT_ID`).
- Защита от второй копии бота: `data/bot.lock`. Две копии делят события и ломают FSM.
- FSM хранится в памяти (`MemoryContext`), поэтому после перезапуска незаконченные заявки теряются.
