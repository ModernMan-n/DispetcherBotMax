# MAX-бот диспетчерской колледжа

## Цель проекта
Бот (позже ИИ-агент) в мессенджере MAX, который принимает заявки в диспетчерскую колледжа по техническим проблемам. Первый этап: пилот в своём колледже. Дальше: превращение в тиражируемый продукт для организаций с диспетчерской (колледжи, вузы, школы, УК, бизнес-центры) с помесячной подпиской.

## Что уже решено
- Бот собирает только: номер корпуса, кабинет, суть проблемы, контакт заявителя в MAX.
- На старте бот работает на личном профиле владельца. Если колледж заинтересуется, бот будет продан колледжу.
- Тестирование только локально, чтобы не собирать персональные данные.
- Нужны БД и дашборд для руководства: скорость выполнения, число закрытых и незакрытых заявок, кто больше закрывает.
- Нужно автоопределение категории заявки.

## Предлагаемый стек (можно менять)
- Python 3.11+
- Библиотека `maxapi` (неофициальная, в стиле aiogram: Dispatcher, Router, фильтры, FSM, polling и webhook)
- SQLite на старте, структура должна легко переезжать на PostgreSQL
- Дашборд: простая веб-страница (FastAPI + шаблон или статический HTML с графиками)
- Токен бота только через переменную окружения `MAX_BOT_TOKEN`, не коммитить в репозиторий

## Заметки по MAX Bot API
- Бота создают через Master Bot (@Masterbot) в MAX, он выдаёт токен.
- При создании есть модерация и требования к оформлению и функционалу бота. Прочитать на https://dev.max.ru/docs-api/ до публикации.
- API: HTTPS-запросы на botapi.max.ru, токен передаётся как access_token.
- К сообщениям можно добавлять кнопки (inline, callback). Использовать кнопки для выбора корпуса и категории.
- При тестировании в групповом чате боту нужны права администратора.
- Если у бота есть активные webhook-подписки, события через polling не приходят. Для локальной разработки использовать polling.
- Не проверено: нужна ли верификация организации для публикации бота от лица колледжа. Уточнить в документации.

## Сценарий заявки (FSM)
1. Приветствие, кнопка «Новая заявка»
2. Выбор корпуса (кнопки из списка в конфиге)
3. Ввод кабинета
4. Описание проблемы (свободный текст)
5. Контакт заявителя берётся из MAX автоматически, при необходимости уточняется
6. Подтверждение, присвоение номера заявки
7. Уведомление заявителю при смене статуса

## Модель данных (черновик)
- `requests`: id, created_at, building, room, description, category, status, applicant_max_id, applicant_name, assignee_id, taken_at, closed_at
- `assignees`: id, name, max_id, active
- `categories`: id, name (например: электрика, сеть и интернет, компьютерная техника, мебель, сантехника, прочее)
- `status_log`: id, request_id, status, changed_at, changed_by

Статусы: `new` → `in_progress` → `done` (плюс `cancelled`).

## Метрики дашборда
- Количество заявок: новые, в работе, закрытые
- Среднее время до взятия в работу и до закрытия
- Нагрузка и количество закрытых заявок по исполнителям
- Просроченные заявки
- Решено 2026-10-08: график «Заявки по дням» и разбивки по корпусам и категориям на дашборде не нужны, их убрали.

## Автокатегоризация
Сначала простые правила по ключевым словам, затем вызов LLM для неоднозначных случаев. Результат должен быть исправляем диспетчером вручную.

## План работ
1. Каркас бота на `maxapi`, FSM сбора заявки, SQLite
2. Панель для диспетчера: взять заявку, сменить статус, назначить исполнителя
3. Уведомления заявителю
4. Дашборд для руководства (эскиз можно показать колледжу раньше готового бота)
5. Автокатегоризация
6. Вынос специфики колледжа в конфиг (корпуса, категории, исполнители, тексты) для подключения новых клиентов
7. Простая админка для настройки организацией

## Границы на старте
- Никаких интеграций с чужими системами до появления второго клиента
- Только бот, БД и дашборд
- Не хранить лишние персональные данные, только необходимое для заявки

## Текущее состояние (2026-10-08)
- Этап 1 готов: FSM заявки на `maxapi==1.2.3`, SQLAlchemy async + SQLite, `org_id` во всех таблицах, автокатегоризация по ключевым словам, генератор демо-БД (`scripts/seed_demo.py`).
- Специфика колледжа уже вынесена в `config/org.yaml`.
- Тесты: `uv run pytest`. Сквозной тест бота (`tests/test_bot_flow.py`) подаёт подставные события MAX через `Dispatcher.handle` без сети.
- Этапы 2–3 сделаны (`app/bot/dispatch.py`): карточка заявки уходит в групповой чат диспетчерской (`dispatcher_chat_id` в `org.yaml`). Кнопки: «Взять», «Готово», «Вернуть в очередь», «Категория» (ручная правка) и «Отменить» с подтверждением. Исполнитель заводится автоматически при первом нажатии «Взять». Заявитель получает уведомления о смене статуса в личных сообщениях.
- Сценарий заявителя работает только в личном диалоге (фильтр `InDialog`). Кнопки карточек принимаются в чате диспетчерской и в личке у специалистов (`CardAccess`).
- Бот проверен на реальном MAX: заявка из личного диалога записывается в БД.
- Особенности MAX API: пустой ответ на callback (`ack()` без `notification`) MAX отклоняет с ошибкой 400. По умолчанию бота нельзя добавить в группу, это разрешается в настройках бота («Приватность»). `GET /chats` больше не поддерживается.
- Этап 4 сделан: дашборд `python -m app.dashboard [--db data/demo.db]`, только 127.0.0.1, без авторизации. Метрики считаются в `app/stats.py`, страница — `app/dashboard/static/index.html` (ванильный JS и SVG, тёмная и светлая тема). Метрики «сейчас» — снимок очереди, «за период» — потоки за 7/30/90 дней. Просрочка определяется по `sla_hours` категории от момента подачи. Персональные данные заявителей на дашборд не попадают.
- После перегенерации `demo.db` сервер дашборда нужно перезапустить: он держит открытым старый файл.
- Специалисты (2026-10-12): `assignees` с `phone`, `on_duty` и направлениями (`assignee_directions`). Направления — это категории из `org.yaml` (добавлена категория 1С), у специалиста их может быть несколько. Вход: `/staff` → кнопка «Поделиться номером». Принимается только контакт, у которого `max_info.user_id` совпадает с отправителем. Новая заявка уходит в чат диспетчерской (он остаётся для обзора) и в личку специалистам направления, которые на линии. Брать и закрывать заявки можно из лички. Все копии карточки записываются в `card_messages` и обновляются вместе (`sync_cards`). При смене категории заявка уходит специалистам нового направления. Специалистов пока заводят командой `scripts/staff.py`, позже это будет админка дашборда.
- Миграций нет (`create_all`). При изменении схемы старую `bot.db` переносили в `data/backup/`. Перед пилотом с реальными данными нужно подключить Alembic.
- Проверено на реальном MAX (2026-10-12): после кнопки «Поделиться номером» в контакте приходят `vcf_info` с номером и `max_info` с профилем владельца. Вход, линия, рассылка новой заявки в личку, «Взять» и «Готово» из лички работают.
- Репозиторий публичный: имя бота, ID чатов и пользователей в файлы не пишем. ID чата диспетчерской задаётся в `.env` (`DISPATCHER_CHAT_ID`).
- Защита от второй копии бота: `data/bot.lock`. Две копии делят события и ломают FSM.
- FSM хранится в памяти (`MemoryContext`), поэтому после перезапуска незаконченные заявки теряются.
